What is Base64?

Base64 is a way of writing binary data using only 64 safe text characters: the letters A-Z and a-z, the digits 0-9, plus + and /. It takes every 3 bytes of input and turns them into 4 characters, which is why the output is about a third longer than the input. When the input length is not a multiple of 3, one or two = signs are added at the end as padding so the decoder knows where the data stops. The text "Hello world" becomes SGVsbG8gd29ybGQ=, and the Arabic word السلام becomes 2KfZhNiz2YTYp9mF. Nothing about the meaning changes. The same text is just written in a form that can travel through systems built for plain text.

Base64 vs Base64URL

Standard Base64 uses + and /, which both have special meanings inside a web address, and it pads the end with =. That is fine for email and config files, but it causes trouble in URLs and tokens. Base64URL fixes that with two small changes.

The two variants hold the same data, so converting between them is only a matter of swapping two characters and adding or removing the padding. Do not mix them up when you decode. Feeding a URL-safe string to a standard decoder, or the other way round, is one of the most common reasons decoding fails.

Why it matters

Some systems only accept plain text. Email was built for text, so an attachment has to be written as text before it can be sent. A web address can only hold a small set of characters safely. A JSON config file cannot hold raw binary at all. Base64 is the bridge that lets binary data cross those text-only systems without being changed on the way. It also shows up in places you touch every day without noticing: the login header your browser sends, the token that keeps you signed in, and the tiny image embedded in a page as a data URL. Knowing how to read it turns a wall of gibberish into something you can check in seconds.

A worked example: from text to Base64 and back

The easiest way to see how Base64 works is to watch the padding change with the length of the input. The word "cat" is 3 bytes, a full group, so it encodes with no padding: Y2F0. Drop one letter and "ca" is 2 bytes, so the output needs one = sign: Y2E=. Drop another and "c" is 1 byte, so the output needs two: Yw==. Shorter input, more padding, and the pattern is exact every time: input length 3 gives no padding, length 2 gives one =, length 1 gives two ==. Try it in the tool above and you will see the same pattern for any text you type. The Arabic word السلام becomes 2KfZhNiz2YTYp9mF with no padding, because its UTF-8 bytes happen to divide evenly into groups of three. Decoding reverses the process: paste Y2F0, pick Decode, and you get "cat" back. If you paste a string and decoding fails, the usual cause is a missing = at the end or a character that is not in the Base64 alphabet, such as a space or a line break left over from copying.

Where Base64 shows up in everyday work

Base64 is easy to miss because it looks like random text, but it is working in places you use every day. Email attachments travel as Base64 inside the message body, because email was built for text and cannot carry raw binary. Small images are sometimes embedded directly in a web page as a data URL, which starts with data:image/png;base64, followed by the encoded image, so the page needs no separate image file. The login header your browser sends for basic authentication is the words username:password encoded in Base64, which is why it must always travel over HTTPS. Tokens that keep you signed in, such as JWTs, hold their header and payload as Base64URL segments separated by dots. Configuration files and API keys are often stored as Base64 so binary values can sit safely inside JSON. Once you can recognise the shape, a long run of letters, digits, plus signs, and slashes ending in = stops looking like gibberish and starts looking like a label you can read.

Common mistakes to avoid

  • Treating Base64 as encryption. Anyone can decode it in seconds, so never encode a password or secret and assume it is hidden.
  • Mixing up the two variants. A URL-safe string fed to a standard decoder, or the other way round, fails or gives the wrong bytes. Check which variant you have before you decode.
  • Losing the padding. Some systems strip the = signs when they store or display a token, and some decoders refuse a string without them. If decoding fails, try adding = signs until the length is a multiple of four.
  • Leaving line breaks in a copied string. Encoded output is sometimes wrapped at a fixed width in emails and documents, and those line breaks have to be removed before decoding.
  • Encoding text twice. Encoding an already encoded string gives you Base64 of Base64, which decodes to the encoded form, not the original text.
  • Forgetting that Base64 makes data bigger. The output is about a third longer than the input, so it is a poor choice for large files where size matters.

Base64 and file size: what to expect

Because every 3 bytes become 4 characters, Base64 output is always about 33 percent longer than the input. A 3 KB text file becomes about 4 KB encoded. A 30 KB image embedded as a data URL becomes about 40 KB inside the page. For small values like tokens and short strings, the extra size does not matter. For large files it does, which is why email attachments and embedded images are kept small and why large files are sent as files, not as Base64 text. If you are embedding an image in a page, a good rule is to keep it tiny, such as an icon under a few kilobytes. Anything bigger belongs in its own file, where the browser can cache it and the page stays fast.

Frequently asked questions

What is Base64 encoding?

It is a way of writing binary data as plain text, using 64 characters: A-Z, a-z, 0-9, + and /. Every 3 bytes of input become 4 characters of output, so the result is about a third longer than the original.

Is Base64 encryption?

No. Base64 hides nothing. Anyone can decode a Base64 string in seconds, with no key and no password. Never use it to hide a password, a secret or a token you want to keep private. It is a transport format, not a lock.

Why does Base64 output end with = signs?

The = signs are padding. Base64 works in groups of 3 input bytes, and when the last group is short, padding marks how many bytes are missing so the decoder can rebuild the original exactly. One = means the last group held 2 bytes, two == means it held 1 byte.

What is the difference between Base64 and Base64URL?

Base64URL replaces + with - and / with _, and usually drops the = padding, so the result is safe inside a web address. Standard Base64 keeps + and / and the padding. Use Base64URL for tokens and URLs, and standard Base64 everywhere else.

Why is my Base64 string longer than the original?

Base64 stores 6 bits per character instead of 8, so it needs 4 characters to carry 3 bytes. The output is always about 33 percent longer than the input. That extra size is the price of making binary data safe for text-only systems.

Is it safe to paste text here?

Yes. The tool runs entirely in your browser. Nothing you type is sent to a server, stored, or logged. Keep in mind that Base64 itself is not private, so do not share an encoded secret and assume no one can read it.

Can Base64 handle binary files, not just text?

Yes. Base64 was made for binary data: images, documents, and any file can be encoded into text and decoded back to the exact original bytes. This tool works with text, but the same idea applies to files, which is how email attachments travel inside a text message.

Why does decoding sometimes give strange characters?

That usually means the original bytes were not plain text, or they were text in a different encoding. Decoding an image or a compressed file gives binary data, which looks like random symbols when shown as text. It can also mean the string was encoded with the wrong variant, so try the other mode.
